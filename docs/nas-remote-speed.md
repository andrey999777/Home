# Почему NAS через интернет даёт 300 КБ/с

Короткий вывод: домашний интернет и диск тут ни при чём.
Узкое место — маршрут «удалённый ПК → VPS в Хельсинки» плюс WebDAV/RaiDrive.
Пока файлы идут через публичный HTTPS WebDAV, 30 ГБ фильм будет копироваться десятки часов.

## Что уже измерено

| Участок | Скорость | Вердикт |
|---|---|---|
| Удалённый ПК, общий интернет (Яндекс.Интернетометр) | 487 / 422 Мбит/с, ping 3 мс | Канал провайдера широкий |
| VPS → домашний файловый сервер | 300 Мбит/с | Туннель до дома **достаточный** |
| Удалённый Windows 10 → VPS | **24 Мбит/с** | Потолок любого копирования *через VPS* |
| Фактическое копирование RaiDrive/WebDAV | **~300 КБ/с ≈ 2.4 Мбит/с** | Протокол режет канал ещё в ~10 раз |

На 30 ГБ это значит:

| Скорость | Время на 30 ГБ |
|---|---|
| 300 КБ/с (сейчас) | ~28 часов |
| 24 Мбит/с ≈ 3 МБ/с (потолок текущего маршрута) | ~2.8 часа |
| 100 Мбит/с при прямом канале РФ↔РФ | ~40 минут |
| 300 Мбит/с как VPS↔дом | ~13 минут |

RaiDrive Premium на скорость WebDAV не влияет: он убирает ограничения бесплатной версии, но не делает HTTP-копии быстрее.

## Как устроена схема сейчас

Публичная точка входа:

- `files.zethixhome.ru` / `nas.zethixhome.ru` → `62.60.152.45` (раньше был `62.60.186.230`)
- Датацентр: **Helsinki, Finland**
- Провайдер VPS: **Aeza (AS210644)**
- Веб-сервер: **Caddy**, HTTPS, HTTP/2, Basic Auth
- Туннель до дома: **Xray reverse** (`nas-bridge` → VLESS Reality `:23630`), не WireGuard

Удалённый ПК со скриншота:

- Публичный IP `91.107.40.23`
- Провайдер: **AVK-computer, Люберцы** (AS48781)
- До Яндекса: 487 Мбит/с и 3 мс — это **российский** пиринг
- До Хельсинки у того же ПК: **24 Мбит/с**

То есть трафик фильма сейчас такой:

```text
Windows 10 (Люберцы, AVK)
    -- HTTPS WebDAV / RaiDrive -->
Caddy на VPS (Хельсинки, Aeza)
    -- уже быстрый туннель 300 Мбит/с -->
домашний NAS
```

Поддержка Aeza права в том, что «порт не режут».
Они не обещают хороший маршрут **конкретного домашнего провайдера Люберец до Финляндии**.
Именно этот hop и даёт 24 Мбит/с.
Домашний NAS при этом до того же VPS отдаёт 300 Мбит/с — у домашнего провайдера международный канал нормальный.

## Почему WebDAV ещё медленнее, чем 24 Мбит/с

24 Мбит/с — это уже мало для 4K remux, но это **3 МБ/с**, а не 300 КБ/с.
До 300 КБ/с схему добивает стек:

1. **WebDAV — плохой протокол для одного файла на 30 ГБ.**
   Много `PROPFIND`/`LOCK`, часто один TCP-поток, мелкие PUT/GET, RaiDrive поверх Windows/.NET.
2. **Caddy как reverse proxy.**
   Без явного streaming буферизует ответ/запрос. Для фильма это даёт рваную скорость и таймауты на хвосте файла.
3. **Высокий RTT до Хельсинки.**
   С маленьким TCP window (типично для WebDAV-клиента) оценка такая:
   `64 КБ / 0.20 с ≈ 2.5 Мбит/с ≈ 300 КБ/с`.
   Это совпадает с тем, что вы видите.
4. Если туннель дом↔VPS когда-то поднимали как **OpenVPN поверх TCP**, поверх него ещё один TCP (HTTPS) даёт классический TCP-over-TCP collapse.
   Текущие 300 Мбит/с VPS→дом говорят, что **этот** hop уже в порядке (скорее WireGuard/UDP).
   Ломается именно кусок Windows→VPS по HTTPS.

Итог: крутить рекламу RaiDrive и писать в поддержку VPS дальше бесполезно.
Нужно сменить **маршрут** и **протокол**.

## Целевая архитектура

VPS должен быть **координатором**, а не обязательным посредником для каждого байта фильма.

```text
                    сигналинг / запасной реле
Windows 10  ---------------- VPS (Хельсинки) ---------------- NAS
     \                                              /
      \---------- прямой UDP (WireGuard/Tailscale) /

фильмы 30 ГБ и 4K-стрим  → только прямой канал
документы / телефон      → можно оставить WebDAV
```

Почему это важно для 30 ГБ:

- 4K Blu-ray remux обычно 40–80 Мбит/с. Через 24 Мбит/с его нельзя ни смотреть напрямую, ни копировать за приемлемое время.
- Если Windows и NAS оба в России, прямой канал почти наверняка упрётся уже в домашнюю отдачу (у вас до VPS она 300 Мбит/с), а не в Финляндию.

Поддержка Aeza как раз про это: клиент Windows должен подключаться **в тот же VPN**, что и NAS, а не ходить на публичный WebDAV.

## План работ по приоритету

Делать по порядку. Каждый шаг сам по себе даёт прирост.

### Шаг 0. Зафиксировать цифры с Windows

На удалённом ПК запустите `scripts/windows-nas-speed-check.ps1`.
Нужны четыре числа:

1. `ping files.zethixhome.ru` — RTT.
2. `tracert files.zethixhome.ru` — где путь уходит в Финляндию.
3. iperf3 до VPS (TCP и UDP) — реальный потолок канала, не speedtest Яндекса.
4. Скачивание **одного большого файла через HTTPS без RaiDrive** (curl/rclone/браузер).

Интерпретация:

| Результат | Что это значит |
|---|---|
| ping 80–200 мс, iperf3 ≈ 20–30 Мбит/с | Маршрут Люберцы→Хельсинки узкий. WebDAV тут ни при чём |
| iperf3 200+ Мбит/с, а RaiDrive 300 КБ/с | Канал живой, убивает WebDAV/Caddy/RaiDrive |
| UDP iperf3 заметно быстрее TCP | Имеет смысл сразу WireGuard, не HTTPS |
| curl/rclone качает несколько МБ/с, RaiDrive нет | Менять клиент, не VPS |

На VPS: `scripts/vps-nas-speed-check.sh`.

### Шаг 1. Сегодня вечером: качать фильм не через RaiDrive

Оставить WebDAV для мелочи. Большие файлы забирать **многопоточным клиентом**.

Вариант A — rclone к тому же WebDAV (часто сразу 10× к RaiDrive):

```bash
rclone copy :webdav:Movies/Film.mkv D:\Inbox\ --progress --multi-thread-streams 8 --retries 5
```

Вариант B — обычный HTTPS, если Caddy отдаёт файл как GET (см. `configs/caddy/Caddyfile`):

```powershell
curl.exe -L --http1.1 -u USER:PASS -o D:\Inbox\Film.mkv https://files.zethixhome.ru/Movies/Film.mkv
```

Ожидание: скорость должна подняться **с 300 КБ/с ближе к 24 Мбит/с** (~2–3 МБ/с).
30 ГБ ≈ 3 часа. Уже можно жить, но это потолок текущего маршрута.

### Шаг 2. VPN на VPS, как советовала поддержка

Поднять **WireGuard** (не OpenVPN-TCP) и включить Windows в ту же сеть, что и NAS.

Готовые шаблоны:

- `configs/wireguard/wg0-vps.conf` — хаб на VPS
- `configs/wireguard/wg0-home.conf` — NAS/домашний сервер
- `configs/wireguard/wg0-windows.conf` — удалённый ПК

После этого в RaiDrive выбрать не WebDAV, а **SMB/SFTP на внутренний IP NAS** (`10.10.0.2`).
Либо вообще Проводник: `\\10.10.0.2\media`.

Ожидание:

- Стабильные ~20–24 Мбит/с вместо 300 КБ/с.
- Иногда UDP-путь у домашнего провайдера лучше, чем TCP/443, и всплывёт 50–100 Мбит/с.
- **Гарантированно больше ширины Люберцы→Хельсинки WireGuard не создаст.**

Обязательные knobs:

- UDP, порт лучше не 51820, если провайдер его режет (например `443/udp` или `51821/udp`).
- MTU 1280–1420. Если скорость «рвётся», начать с `MTU = 1280`.
- `net.ipv4.ip_forward=1` на VPS.
- У пиров `AllowedIPs` друг на друга, иначе Windows не достучится до NAS.

### Шаг 3. Прямой канал, без Финляндии на каждом байте

Это единственный способ комфортно возить 30 ГБ и смотреть 4K remux.

Самый простой вариант — **Tailscale** (или Headscale на этом же VPS, если не хотите чужой control plane):

1. Tailscale на NAS и на Windows.
2. В админке выключить «force relay», оставить DERP только как запас.
3. Проверить: `tailscale status` / `tailscale ping <nas>` должно быть **direct**, не `relay`.
4. Диск: `\\nas\media` или RaiDrive → SMB на Tailscale-IP.

Если direct не поднимается (жёсткий NAT с обеих сторон) — VPS остаётся DERP/реле, и вы снова в 24 Мбит/с.
Тогда либо проброс UDP на домашнем роутере, либо IPv6 на одной из сторон, либо VPS **в Москве**.

Альтернатива без Tailscale: второй WireGuard peer-to-peer endpoint дом↔Windows, VPS только раздаёт ключи. Это сложнее в сопровождении.

Ожидание при direct: десятки–сотни Мбит/с, фильм за 10–40 минут.

### Шаг 4. Если нужен именно просмотр, а не копия

Копировать 30 ГБ на удалённый диск не обязательно.

- **Jellyfin/Plex/Emby** на NAS, наружу через Caddy.
- Для 4K remux прямой канал из шага 3 обязателен (24 Мбит/с не хватит).
- Если прямого канала нет — транскод в 1080p ~8–15 Мбит/с. Это уже влезает в 24 Мбит/с, ценой CPU домашнего сервера.

### Шаг 5. Необязательно: перенос VPS ближе

Если Tailscale/WG direct не получается, а фильмы нужны часто:

- Тот же Aeza, локация **Москва**, а не Helsinki.
- Либо Selectel / Timeweb / любой VPS в ММТС-9.

Тогда даже реле Windows→VPS→NAS будет российским пирингом, и 24 Мбит/с с большой вероятностью превратятся в сотни.
Текущий Хельсинки имеет смысл оставлять для «европейского IP», VPN и сайтов — не для домашних фильмов.

## Что поправить в Caddy, если WebDAV оставляете

Файл: `configs/caddy/Caddyfile`.

Минимум:

- `flush_interval -1` — не буферизовать фильм целиком.
- Не ставить `request_buffers` / `response_buffers`.
- Таймауты 24h, не дефолтные 30–60s.
- `request_body { max_size 0 }` или очень большой лимит, иначе 413 на закачку.
- Для RaiDrive часто стабильнее **HTTP/1.1**, чем HTTP/2. В шаблоне это уже заложено.
- Отдельный `handle_path` для «скачать файл целиком» удобнее WebDAV.

WebDAV после этого останется удобным «диском в Проводнике» для документов.
Для фильмов его всё равно не стоит использовать.

## Чего не делать

- Не ждать, что Premium RaiDrive разгонит канал.
- Не просить Aeza «открыть скорость»: порт у них и так широкий, узкое место в маршруте AVK→Finland.
- Не включать OpenVPN-TCP «чтобы точно пролезло». Для фильмов это худший транспорт.
- Не гонять 4K remux через публичный HTTPS, если есть любой прямой VPN.
- Не измерять успех Яндекс.Интернетометром: он ходит в российский CDN, а ваши файлы — в Хельсинки.
